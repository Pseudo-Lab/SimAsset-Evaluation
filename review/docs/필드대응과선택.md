# 결과 파일과 검토 기록의 연결

공유된 DB v0.1 제안을 참고해 결과 수신·판정 흐름에 필요한 부분을 별도 `review` 스키마로 구현했습니다. 기존 공동 DB를 수정하지 않았습니다. 결과 파일 어댑터와 화면을 먼저 검증하고, 최종 스키마가 정해지면 대응을 바꿀 수 있게 했습니다.

## 필드 대응

| 출력·입력 | 저장 위치 | 적용한 처리 |
| --- | --- | --- |
| `asset_id` | `assets.source_object_id` | 출처 namespace 안에서 구분합니다. 표시 이름만으로 원본을 합치지 않습니다. |
| `asset_sha256` | `asset_variants.content_hash` | 출력에서 선언한 해시입니다. 원본 모델까지 검증한 것으로 표시하지 않습니다. |
| `test`, 검증기 버전 | `test_protocols` | `incline`과 `incline-env-v3-adapter-1`을 사용합니다. 후자는 팀 규약 승인 버전이 아닙니다. |
| 조건·적용 물성·접촉 설정 | `test_cases.config`, `test_runs.raw_meta` | 조건 해시로 묶고 원래 JSON도 보존합니다. 실제 난수 교란과 초기 자세는 실행 기록에 남깁니다. |
| `run_id` | `test_runs.source_run_id` | namespace와 원본 ID로 실행을 구분합니다. 같은 ID·다른 내용은 충돌입니다. |
| seed | `test_runs.seed` | 정수만 받습니다. repeat 번호는 원본에 없어 현재 NULL입니다. |
| MuJoCo·Git commit | `engine_version`, `harness_commit` | 없는 값은 추정하지 않습니다. 재현 래퍼는 다른 저장소의 commit이 원본 코드 commit으로 찍히지 않도록 중립 작업 폴더에서 실행합니다. |
| `status` | `source_status`, `execution_status` | 원본 상태와 처리 상태를 모두 보존합니다. 사람 판정과 별개입니다. |
| metric/value/unit | `metric_definitions`, `run_metrics` | mm→m, deg→rad, %→비율로 변환하고 원본 값·단위를 함께 보존합니다. |
| NaN·빈 값 | `valid=false`, NULL, 사유 | 0으로 바꾸지 않습니다. 텍스트 지표도 별도로 저장합니다. |
| 시계열·영상·그림 | `run_artifacts` | 사본의 SHA-256, 크기, 파일명을 기록합니다. 시계열 그래프는 원본 mm 단위를 표시합니다. |
| 사람 판정·메모 | `run_judgments` | 평가자·항목·기준 버전·근거 파일·이전 판정 ID를 남깁니다. 수정은 새 행입니다. |
| 입력 시도 | `import_attempts` | 성공·중복·충돌·검증 실패를 기록합니다. |

원본 11개 CSV 열과 시계열 16개 열의 순서·단위·유한값·ID 일관성을 확인합니다. 예상하지 않은 출력 버전은 자동 추측해 가져오지 않습니다. 기본 한 묶음 제한은 100개 파일·256 MiB, CSV는 파일당 32 MiB입니다.

## 선택 이유와 대안

| 선택 | 이유 | 다른 선택지·바꿀 조건 |
| --- | --- | --- |
| 파일 묶음 수신 | 현재 하네스의 출력 방식으로 재전송·보존·오류 확인이 가능합니다. | 작업 수가 많아지면 업로드 API·작업 큐를 추가합니다. |
| 사본 보존 후 검증 | 가져오는 동안 원본이 바뀌어도 어떤 바이트를 검증했는지 남습니다. | 원격 객체 저장소는 공동 보관 기간과 접근 권한이 정해지면 연결합니다. |
| namespace + 원본 ID | 충돌하는 제공자·배치를 분리하고 조용한 덮어쓰기를 막습니다. | 팀 공통 실행 UUID가 생기면 그 값을 채택합니다. |
| 별도 로컬 스키마 | 공유 설계를 검증하면서 공동 DB에 영향을 주지 않습니다. | 19개 테이블의 최종 필드가 합의되면 마이그레이션·어댑터를 작성합니다. |
| Grafana 조회 + 별도 판정 화면 | 조회 권한과 이력이 있는 입력을 분리할 수 있습니다. | 조회·입력을 하나의 웹앱으로 통합하거나 입력 플러그인을 평가할 수 있습니다. |
| 통과·실패·보류 | 기준이 미정이어도 검토 흐름을 시험할 수 있습니다. | 성준님의 기준에 따라 항목·필수 근거를 바꾸고 기존 판정 버전은 유지합니다. |

현재 동일 원본 ID를 반복 생성하는 하네스는 실행마다 고유 ID를 주지 않습니다. 개인 벤치마크는 반복별 출력 폴더와 namespace를 달리해 보존했습니다. 따라서 namespace 사이의 같은 에셋을 하나의 팀 자산으로 자동 통합하거나 반복 번호를 추정하지 않습니다. UI의 에셋 필터는 표시 이름 기준이며, 팀의 canonical asset ID 연결은 후속 작업입니다.

## 출력 코드에서 확인한 빈틈

원본에는 명시적 규약 버전·repeat 번호·실행 시작/종료 시각이 부족합니다. 파일을 가져온 시각은 실제 실험 시각과 구분합니다. 일부 예외 경로는 `summary.csv`만 쓰고 `meta.json`을 남기지 않습니다. 이 경우 입력기는 자료 누락으로 기록합니다. 없는 실행 정보를 만들어 넣지 않습니다.

`missing_inertial`과 문서의 `missing_inertia`는 모두 오류로 대응하되 원래 문자열을 유지했습니다. `ok`, `unsettled`, `diverged`는 실행이 결과를 냈다는 처리 상태이며 물체의 합격을 뜻하지 않습니다. 홈 검사 등의 `not_applicable`은 별도 skipped로 기록합니다.

## 팀에 확인할 질문

1. 실행 ID에 에셋 버전·검사 규약·seed·자세·반복 번호를 어떻게 넣을까요?
2. 같은 실행의 결과 수정은 새 실행으로 발급할까요, 원래 실행의 새 산출물 버전으로 둘까요?
3. 규약 버전·시작/종료 시각·반복 번호와 예외 시 `meta.json`을 공통 writer에서 보장할까요?
4. 판정 항목과 필수 근거, 보류 사유를 어떤 기준으로 맞출까요?
5. 영상·그래프·전체 시계열의 보관 기간과 원본 공개 범위는 어떻게 둘까요?
6. 서로 다른 제공자의 같은 에셋과 직접 보완한 에셋을 어떤 ID 관계로 연결할까요?

실제 팀의 50개 결과 묶음과 나머지 검사별 출력은 아직 이 입력기로 대조하지 않았습니다. 이번 검증은 공유 코드의 샘플 직접 재현과 별도 기능 시험을 구분합니다.
