# 결과 묶음 점검

결과를 DB에 넣기 전에 폴더·파일·실행 ID와 검사별 형식을 확인합니다. `audit`는 원본과 DB를 변경하지 않습니다. 출력의 `valid`는 파일 검증 상태이며, 에셋의 품질 판정은 검토 화면에서 별도로 남깁니다.

## 입력과 명령

결과 폴더는 실행별 하위 폴더를 포함할 수 있습니다. 예상 실행 목록이 있으면 배치와 대조합니다. 목록에는 결과 폴더 기준 상대 경로, 에셋 ID, 검사, 조건, 시드, 필요한 근거 파일을 적습니다. 목록은 검사 계획을 기준으로 준비해야 제출되지 않은 실행도 찾을 수 있습니다. 형식은 [예상 목록 예제](../examples/expected-settle-v4.json)와 [결과 제출 안내](결과제출_계약초안.md)를 참고하세요.

저장소의 `review/`에서, 경로를 실제 배치와 목록에 맞춰 실행합니다.

```bash
uv run simasset-review audit "/path/to/batch" --expected "/path/to/expected.json"
```

예상 목록 없이 현재 있는 파일을 점검할 때는 `--expected`를 생략합니다. 명령을 처음 써보려면 [가만히 두기 v4 샘플](../README.md#샘플로-확인)로 시작하세요.

## 결과 읽기

- `ready_for_import: true`이면 발견한 결과가 형식 검증을 통과했습니다. `expected_coverage_verified: true`까지 확인하면 제공한 예상 목록과 실행·필수 파일이 모두 일치합니다. `--expected` 없이 점검하면 전체 제출 여부는 알 수 없습니다.
- `ready_for_import: false`와 종료 코드 `2`가 나오면 `records`의 문제 경로와 코드를 확인합니다. 예상 목록 자체를 읽지 못한 경우에는 최상위의 `code`와 `message`를 봅니다.
- 형식이 유효한 실행도 영상이나 일부 메타데이터가 빠질 수 있습니다. `warnings`에 표시된 항목을 보고, 팀 검토에 필요한 근거가 있는지 확인합니다.

| 오류 코드 | 확인할 일 |
| --- | --- |
| `missing_result`, `missing_file`, `missing_artifact` | 누락한 실행이나 파일을 검사 담당자에게 확인합니다. |
| `unexpected_result`, `expected_identity` | 다른 배치가 섞였는지, 에셋·검사·조건·시드가 계획과 다른지 확인합니다. |
| `duplicate_run` | 내용이 같은 실행이 여러 곳에 있습니다. 적재할 원본 위치 하나를 정합니다. |
| `conflicting_run` | 실행 ID가 같고 내용이 다릅니다. 양쪽 원본을 보존하고 재실행이나 수정본의 식별을 먼저 맞춥니다. |
| `unsupported_profile`, `metric_or_unit` | [도구의 지원 범위](../README.md#가져오기-지원-범위)와 [검사환경 공통규약 v4](../../docs/검사환경-공통규약-전체본_v4.md)를 대조합니다. |

## 적재 담당자에게 전달

- 배치 이름과 실제 공유 경로 또는 MinIO에서 사용 중인 경로
- 예상 목록과 점검한 범위, 유효·무효 개수, 조치가 필요한 경로·오류 코드
- 적재에 사용할 `namespace`와 `origin`. 같은 배치를 다시 가져올 때 동일한 `namespace`를 써야 중복이나 충돌을 확인할 수 있습니다.

팀 서버는 [이미 병합된 공유 버킷 동기화 도구](https://github.com/Pseudo-Lab/SimAsset-Evaluation/pull/5)와 [컨테이너의 결과 가져오기 절차](../../.devcontainer/README.md#결과-가져오기와-테스트)에 연결합니다. 버킷 폴더 구조 변경은 [이슈 #6](https://github.com/Pseudo-Lab/SimAsset-Evaluation/issues/6)에서 논의 중이므로, 전달할 때는 현재 실제 공유한 경로를 적습니다.
